# Epic 3: MCP Diagram Generation + Wrappers

## Goal

Implement `diagram_generate_from_prompt` so that the IDE can create a new editable diagram JSON file and initial SVG artifact from a natural-language prompt, and implement `diagram_render` so that saved diagrams can be re-rendered on demand.

## User Scenario

A user asks the IDE agent to create a diagram. The IDE agent calls `diagram_generate_from_prompt` with a prompt, diagram type, and workspace directory. GraphPilot derives a name from the prompt/content and saves a new `<name>.gp.json` under `.graphpilot/diagrams/`, renders an initial `<name>.svg` beside it, and returns the file paths and an `editUrl`. The user can open the edit URL in the React editor (Epic 2, with the S05 renderers) and immediately see the generated diagram. Later, the user or IDE agent calls `diagram_render` to refresh the SVG from the latest saved file.

## Scope

- `diagram_generate_from_prompt` MCP tool implemented
  - inputs: `prompt`, `diagramType`, `workspaceDir`, optional `style`
  - output: `diagramPath`, `svgPath`, `editUrl`
  - supported diagram types: `activity_diagram`, `use_case_diagram`, `bdd_diagram`
- `PromptDiagramGenerationService` implemented
  - **LLM-backed generation via Azure OpenAI** (Azure AI Foundry; deployment configurable, default `5.4`, with `5.4-mini` available — see `docs/03-development-and-delivery/03-deployment-and-distribution-options.md`). For dev/MVP the key lives in `.env`; the central key proxy is a later hardening concern. The LLM client is an injectable seam so unit tests run offline against a fake
  - produces GraphPilot JSON that matches the canonical schema
  - conforms output to the diagram type's vocabulary (the `diagram_types.py` type profile), using the `examples/<name>/{prompt.md, output.gp.json}` answer keys + per-type `prompts.md` as context (the `default.json` blueprints were retired in Epic 2), then strict-checks / repairs the result against that vocabulary
  - stamps `metadata.authoring = "generated"` — now **informational provenance** only (authoring no longer drives strictness). Strictness is decided by `diagramType`: generation conforms output to the `diagramType` vocabulary and rejects `diagramType="custom"` (valid to save/validate, not generatable). The shared `DiagramValidationService` runs the per-type structural critic as advisory Layer 4 warnings for every diagram; generation pipelines escalate residual findings to a hard block
  - validates generated JSON before final save
  - calls render after save to create the initial SVG artifact
- a uniquely named diagram file allocated under `.graphpilot/diagrams/` for each generated diagram (name generated by the MCP server, then passed to `WorkspaceStorageService.create_diagram`, which sanitizes the name and de-duplicates on collision)
- `diagram_render` MCP tool implemented
  - input: `diagramPath`
  - output: `svgPath`
- `DiagramRenderService` implemented
  - loads a saved `<name>.gp.json`
  - renders SVG with the **`drawsvg`** library, **honoring the saved node coordinates** (no re-layout), and writes the sibling `<name>.svg` beside the source file
  - fails cleanly on missing or malformed input
- reuses shared services: `WorkspaceStorageService`, `DiagramValidationService`, `DiagramTypeService`, `SchemaRegistry`
- edit URL shape: `http://localhost:5173/editor?diagramPath=<absolute-path>`

## Out of Scope

- `diagram_update` and IDE-based diagram editing (Epic 4)
- `diagram_apply_patch` and structured patch operations (deferred post-MVP)
- React frontend / editor rendering changes (Epic 2)
- browser-facing API routes (Epic 2)
- the comprehensive answer-key sample library (delivered by Epic 2 Slice 08)
- RAG example lookup (Epic 5)
- PDF export (deferred); SVG uses `drawsvg` and PNG is now available through the shipped `resvg-py` raster path
- generation evaluation / DOE — the former narrow answer-key evaluator and runner were removed pending an embeddings-based post-MVP rebuild; the curated training/eval pools remain
- multi-provider LLM routing or blueprint routing (generation uses **Azure OpenAI** with a single configurable deployment; choosing across providers stays out of scope)
- standalone repair or autofix flows (generation still does its own internal conform/repair of the LLM output against the type vocabulary before validation)
- database persistence
- auth
- Docker

## Implementation Plan

Build bottom-up so each layer is testable before the next depends on it. Design detail lives in the design docs (`03-rendering-design.md`, `04-generation-design.md`); this is the build order:

1. **Render** — `DiagramRenderService` (`drawsvg`) + `diagram_render`: saved JSON → `.svg`, honoring the saved coordinates. Lets us *see* what the later steps produce.
2. **Layout** — the sole pinned `PyGraphvizLayoutEngine` turns a logical graph into positioned nodes and is independently testable against the answer keys.
3. **Generation core** — `PromptDiagramGenerationService`: prompt → logical LLM output → conform → size → layout → assemble → validate → save → render. The LLM client is an injectable seam (offline tests).
4. **`diagram_generate_from_prompt` tool** — expose the service over MCP (paths + `editUrl`).
5. **Example library overhaul** — re-curate + expand the examples into a **training pool** (few-shot) and a held-out **eval pool**.

> **Eval + DOE removed (pending redesign):** the original plan added an eval framework and a generation DOE as a final testing step; both — and their code — were removed for an embeddings-based rebuild. See `../../../02-design-and-features/07-evaluation-and-doe-design.md`.

Shared services (`WorkspaceStorageService`, `DiagramValidationService`, `DiagramTypeService`) are reused throughout; the Azure key lives only in a local `.env`.

## Context-backed generation extension

Epic 3's original direct-prompt generation and rendering core remains complete. The
[`04-context-backed-generation/`](04-context-backed-generation/00-group.md) phase is a separately tracked
extension that adds evidence manifests, request contexts, readiness, provenance, context-backed generation, and
its MCP workflow while preserving direct generation. Its coordinated taxonomy broadens shared storage/schema
infrastructure, gives prompt/context diagram generation symmetric names, and creates a dedicated readiness
package; each owning slice updates runtime imports and active docs atomically. Group-local Slice 12 adds a same-name
prompt/tool compatibility bridge for tools-only MCP clients without executing the workflow. The extension uses
`01`–`12` numbering rather than continuing the historical numbers above.

Implementation discoveries update the active design owner and affected future slices in the same change; each
slice records deviations and verification in its `## Outcome`. Historical research remains rationale after
promotion, not implementation authority.

## Acceptance Criteria

- `diagram_generate_from_prompt` can be called from an IDE MCP client
- a valid `<name>.gp.json` is written under the workspace's `.graphpilot/diagrams/`
- the generated diagram JSON passes `DiagramValidationService` validation
- an initial `diagram.svg` is created beside the JSON file
- the returned `editUrl` opens the diagram in the React editor (Epic 2 + S05 renderers)
- all three MVP diagram types (`activity_diagram`, `use_case_diagram`, `bdd_diagram`) can be generated
- `diagram_render` loads a saved diagram and writes a fresh `diagram.svg`
- unsafe or missing paths are rejected
- invalid generated output is not saved

> The catalog-driven conform/render + authoring model is delivered in Epic 1's **`04-universal-vocabulary`** group
> (`../01-local-diagram-foundation/04-universal-vocabulary/00-group.md`), reusing this epic's answer-key engine
> (S11) and eval (S06) — not further Epic 3 slices. The **new diagram types** (state machine, class,
> requirement, IBD) are **deferred post-MVP** (their vocab lives in the schema doc §7).
