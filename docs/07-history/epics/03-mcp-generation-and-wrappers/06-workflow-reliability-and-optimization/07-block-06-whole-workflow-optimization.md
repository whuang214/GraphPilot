# Block 6: Whole-Workflow Optimization

## Goal

Aggressively reduce complete user-visible workflow time, provider/host resource use, repair frequency, timeout risk, and
failure rate by optimizing every worthwhile contributor while preserving causality, quality, security, and compatibility.

## Input

Block 5 supplies one complete controlled live anchor, a rerun provider-free Block 1 critical path, a user-supplied external Copilot cold observation, and a ranked two-lane backlog. The controlled anchor labels pre-authored JSON 1/JSON 2 as prepared/imported and leaves real host authoring as an external gap. The external observation belongs to a different Todo repository/request and is not a shared percentage denominator. Block 6 does not optimize unmeasured stages or assume historical S13–S15 bottlenecks remain dominant after readiness/workflow changes.

## Question This Block Owns

Which evidence-backed changes, applied in measured waves, produce the largest cumulative improvement to the complete
request-to-visible-diagram journey without weakening the shared success contract?

## Causal Lanes

- **Lane A · Host/integration preparation:** optimize only GraphPilot-controlled host contracts and reference workflows—backend derivation of values a host cannot know, actionable validation and relationship-closure guidance, compact JSON 1/JSON 2 summaries/templates, reuse of current JSON 1, bounded instructions, and duplicate-read/readiness avoidance. Do not modify the host agent or claim control over its model, index, or cache.
- **Lane B · GraphPilot workflow/business logic:** prioritize avoidable provider calls and contract validity, then packet/cache/sequence/MCP contributors. Local deterministic code is eligible only when measured contribution supports it; “business logic speed” is not permission for arbitrary Python micro-optimization.

Host/interface and provider/runtime changes never share one measurement wave. Generation and semantic-review first-response failures remain separate owners unless provider-free diagnosis proves one cause.

## Host Measurement Prerequisite

A measured host-wall claim requires strict external observations from a host that is not the agent performing the work: one cold run from missing JSON 1 and one warm run reusing current JSON 1, each recording repository commit, request digest, host/version, model identity, cache state, searches, focused reads, bytes, authoring attempts, validation retries, elapsed wall, exposed tokens/credits, and JSON 1/JSON 2 digests. External host profiles and the controlled GraphPilot anchor remain separate denominators; percentages are never forced across incompatible repositories or requests.

Lane A's host was retargeted from GitHub Copilot to Devin CLI, which is also the agent implementing the changes. That host cannot produce measured wall-time evidence, so **no such profile exists and none is planned**. Lane A therefore contributes only provider-free characterized results to the cumulative ledger, permanently labeled as such, and the host domain of the performance split stays `not_measured` with that reason.

A host-facing change may still be retained when it fixes a demonstrated deterministic contract or usability defect, provider-free evidence shows fewer required corrections or a smaller and clearer contract, compatibility, authority, and safety remain intact, and independent audit passes. Lane A's exit gate is the cold completion criterion rather than a wall-time delta: a cold host, using only what MCP returns, produces valid JSON 1 and JSON 2 in at most two attempts each.

## Lane A Host Workflow Design

The approved GraphPilot-controlled host lane is defined by the [Lane A host workflow design](06-whole-workflow-optimization/history/lane-a/lane-a-host-workflow-design.md); its current state and next package live in the [Lane A plan](06-whole-workflow-optimization/lane-a/plan.md), and its original dependency-ordered execution plan is retained as [history](06-whole-workflow-optimization/history/lane-a/lane-a-00-group.md). It defines a small structured route tool, one selected mode/type authoring-contract lookup, a replaceable current evidence snapshot, durable saved requests, conditional BDD completeness guidance, proportional Todo cold/warm measurement, and provider-free-before-live integration. The user authorized plan execution, while Copilot benchmark sessions and every live provider call retain their exact later gates.

## Optimization Surface

Consider all measured contributors:

- host routing, source searches/reads, context growth, JSON 1/JSON 2 authoring/reconciliation, tokens, and credits;
- readiness input/response validity, repair, reasoning effort, provider caching, and policy processing;
- generation packets/examples, strict generation, deterministic repair, semantic review/response/candidate repair/final
  review;
- provider deployment/service tier, call sequencing, bytes, tokens, caching, and failure behavior within approved controls;
- MCP process/discovery/transport/serialization/progress/timeout/recovery;
- local schemas/rubrics/examples, validation, digests, persistence, layout, canonical assembly, provenance, rendering;
- API/editor bundle/load/render completion.

Small repeated savings are valid when their cumulative user-visible benefit exceeds risk and maintenance cost. Large
provider/host savings remain prioritized, but inexpensive safe local improvements need not be ignored merely because they
are individually small.

## Optimization Waves

Block 5 ranks the first waves as: (1) semantic-review first-response contract (`finding_invalid @ $`, 37,787.5872 ms repair), (2) generation endpoint contract (`bdd_relationship_endpoints_invalid @ $.edges[3]`, 26,052.5176 ms repair), and (3) host relationship-closure interface, whose wall benefit remains pending strict external measurement. This order follows comparable measured contribution and confidence; the larger external host delay is causal evidence but not yet a bound warm denominator.

Maintain a ranked backlog and execute one owner or tightly related cause cluster at a time:

```text
measure baseline
→ implement one coherent wave
→ run smallest proof
→ rerun anchor and quality guard set
→ compare complete wall/calls/tokens/credits/repairs/reliability
→ keep or revert
→ update cumulative baseline and backlog
```

Several changes may share a wave only when their effect cannot be evaluated meaningfully in isolation and the combined
owner remains clear. Unrelated host/provider/backend/frontend changes remain separate.

## Cumulative Ledger

For every candidate and retained wave, record:

- baseline/candidate code and asset identities;
- absolute and percentage complete-wall effect;
- host read/token/credit effect;
- Azure role/call/token/cache/repair effect;
- MCP/local/browser effect;
- reliability and timeout effect;
- quality/security/compatibility outcome;
- proof coverage, rollback, and cumulative total;
- claim state: measured, provider-free characterized, or pending external host rerun.

The current accepted baseline replaces older baselines after each retained wave. Incomparable case/config/provider versions
are never presented as direct savings.

## Guard Set

Every wave reruns the Block 5 anchor plus a small fixed guard set that includes a fail-closed readiness boundary and enough
nontrivial deterministic/semantic coverage to catch obvious overfitting. Block 7 supplies broader validation after the main
optimization waves.

## Stop Conditions

Stop Block 6 when no remaining material contributor has a supported fix, marginal benefit is disproportionate to
complexity/risk/live cost, quality or reliability would weaken, or remaining work is speculative. A long backlog alone is not
proof that every item should be implemented.

## Outputs

- Ranked optimization backlog and wave plans.
- Before/after and cumulative ledger.
- Retained/reverted changes with exact evidence and commits.
- Updated anchor baseline and reusable Block 1 audit results after material waves.
- Optimized candidate package for Block 7.
- Deferred opportunities with rationale and trigger for reconsideration.

## Exit Gate

The dominant material contributors are addressed or explicitly deferred; retained changes produce meaningful cumulative
user-visible benefit; anchor/guard quality and recovery remain safe; measurements are current and causal; and the optimized
candidate is ready for representative validation.

## Not Owned Here

- Weakening authority, readiness, strict output, reviewed quality, provenance, persistence, or parity for speed.
- Async/progress work presented as reduced provider latency.
- Broad stability/certification claims from anchor cases.
- Automatic promotion of any retained change.

## Block-Agent Handoff

Each optimization agent owns an approved wave, not the entire backlog. It returns baseline/candidate evidence, retained or
reverted decision, cumulative ledger update, quality/guard results, checks/commits, rollback, and the next ranked candidate.
The high-level reviewer controls wave order and Block 6 completion.
